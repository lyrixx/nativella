# AGENTS.md

Instructions for AI agents working on this repository.

Nativella runs a PHP web application as a desktop application: a Tauri 2 shell in Rust
(`crates/nativella`) hands every request of the webview to PHP through a custom SAPI
(`crates/runtime`). The repository holds the crates, the PHP packages, the demos, the website and
the documentation. The Docker/Castor workflow is described in
[docs/development.md](docs/development.md).

## Layout

| Path | What |
|---|---|
| `crates/runtime` | `nativella-runtime`: the SAPI, the PHP thread, `nativella_call()` |
| `crates/nativella` | `nativella`: the Tauri shell, the native APIs, `nativella build` |
| `packages/nativella` | The PHP client of the native APIs, framework-agnostic |
| `packages/symfony`, `packages/laravel` | The Symfony bundle, the Laravel package |
| `demos/symfony`, `demos/laravel`, `demos/vanilla` | The demos, on `packages/*` through a Composer path repository |
| `website/` | The website: the landing page, generated by a PHP script, and the documentation (`docs/*.md`), built by MkDocs |
| `infrastructure/docker/`, `castor.php`, `.castor/` | The Docker stack and its tasks |
| `tools/` | The tools: PHP CS Fixer, PHPStan and Twig CS Fixer, one Composer project each, and MkDocs, in a Python virtual environment |

Every directory of `packages/*` and `demos/*`, and `website/`, with a `composer.json` is a
project: the Castor tasks find them at each run, a new one needs no configuration.

## Fundamental rule: PHP and Composer run in the builder

Never run PHP or Composer on the host. Everything goes through the `builder` container, via
Castor, from the root of the repository:

```bash
castor builder -- composer require foo/bar -d demos/symfony   # one-off command
castor builder                                                # a shell, in /var/www
```

The builder also holds the Rust toolchain, libphp and WebKitGTK: the crates build and are tested
there (`castor qa:rust`), in their own target directory (`target/docker/`).

**The exceptions are the desktop application and the mobile builds**:

- a window needs the display, so `castor nativella:run <demo>` runs cargo on the host (it needs
  the system packages of [docs/installation.md](docs/installation.md)). `--docker` runs it in the
  builder instead, on the Wayland/X11 display of the host;
- the builder has no Android SDK, so `castor mobile:android <demo>` runs
  `mobile/android/build.sh` on the host, with its PHP, Composer, SDK and JDK (see
  [docs/mobile.md](docs/mobile.md)): the task lists what is missing.

Host prerequisites: Docker, Castor (and, for `nativella:run` on the host, Rust and the Ubuntu
packages).

## Essential commands

```bash
castor start                     # build + install + website + migrate + up
castor stop                      # stop the stack
castor install                   # composer install in every project, + the tools
castor migrate                   # migrate the databases of the demos, for the frontend
castor website:build             # website/dist/, and the documentation in website/dist/docs/
castor nativella:run symfony     # the Symfony demo, as a desktop application (host)
castor nativella:smoke           # each demo answers through the runtime, without a window
castor nativella:build [demo]    # dist/nativella and the standalone executables of the demos (staged for production)
castor mobile:android symfony    # an Android APK of the demo (host)
castor logs [--service=service]  # logs (frontend, router)
```

The frontend serves `https://nativella.test` (the website) and `https://<demo>.nativella.test`
(`demos/<demo>/public`, without the native features).

## QA — before considering a task done

```bash
castor qa [--dry-run]            # everything below
castor qa:cs [--dry-run]         # PHP CS Fixer (.php-cs-fixer.php), Symfony style
castor qa:twig-cs [--dry-run]    # Twig CS Fixer (.twig-cs-fixer.php)
castor qa:phpstan [--project=demos/symfony]   # PHPStan level 8, project by project
castor qa:phpunit [--project=demos/symfony]   # PHPUnit, or `php artisan test` for Laravel
castor qa:rust                   # cargo fmt --check, clippy -D warnings, cargo test
castor qa:security-audit         # composer audit
```

After a PHP or Twig change: `castor qa:cs --dry-run`, `castor qa:phpstan`, then
`castor qa:phpunit`. After a Rust change: `castor qa:rust` and `castor nativella:smoke`.

PHPStan runs from the directory of each project, so that it finds its classes through its own
`vendor/`. A project without a configuration of its own is analysed with
`tools/phpstan/project.neon` over its PSR-4 directories; one that needs more (an extension, a
baseline) adds a `phpstan.dist.neon` that includes it.

## Castor contexts

```bash
castor --context=ci ...          # what the GitHub Actions workflows use
```

There is no `test` context: each test suite sets its own environment (`phpunit.xml`).

## Conventions

1. **Never invoke `docker compose` by hand**: use the `docker_compose()` /
   `docker_compose_run()` functions from `.castor/docker.php` to write new tasks.
2. **Never hardcode ports or project names**: git worktree support automatically
   isolates project/volumes/ports. Use `variable('project_name')` etc.
3. **Never hardcode the list of projects or demos**: use `project\all()` and `project\demos()`
   from `.castor/project.php`.
4. New recurring task? Make it a Castor task (`castor.php` or `.castor/*.php`),
   not a shell script.
5. Tool dependencies live in `tools/<tool>/` (`composer.json`, or `requirements.txt` for MkDocs),
   not in the projects.
6. The CI (`.github/workflows/`) runs Castor tasks only, with `CASTOR_CONTEXT=ci`: what passes
   locally passes there.
